# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A custom OpenAI Gym-style RL environment (`DevOpsEnv`) where a language model acts as an
on-call SRE, choosing from a 19-action space to diagnose, mitigate, and resolve one of 6
incident scenarios. Mitigations are gated on diagnosis (`env/models.py::MITIGATION_PREREQS`):
applying one before its prerequisite diagnostic is a no-op that increments
`harmful_action_count`, closing an exploit where a beam search could resolve tasks by
guessing the fix and back-filling the inspects. The model is trained with a two-phase
pipeline — SFT warm-start on 4 held-in tasks, then GRPO primarily rewarded by exact Q\*
(`training/qstar.py`) over an eps-greedy-expanded state distribution — using Unsloth + TRL
on Colab. `memory_leak` and `disk_full` are held out of both training phases entirely. Full
project background, scenarios, reward signals, and API surface are documented in `README.md`
and `openenv.yaml` (the OpenEnv spec) — read those before making non-trivial changes to
`env/`, `graders/`, `tasks/`, or `training/`.

## Architecture

**Data flow:** `env.environment.DevOpsEnv` (reset/step/state/episode) is the gym-style core.
`step()` computes reward as the *delta* in `graders.grader.compute_score()` between before
and after the action, then layers on explicit penalties/bonuses (no-op penalty, repeated
inspect-action penalty, mitigation-without-diagnosis penalty, communication bonus,
early-resolution efficiency bonus, harmful-action-rate penalty) and clamps to `[-0.25, 1.0]`.
Before applying any mitigation's effect, `_apply_action` checks it against
`env.models.MITIGATION_PREREQS` via the shared `_mitigation_effective()` helper — an
unmet prerequisite makes the action a no-op that only increments `harmful_action_count`,
recorded in `self._state["effective_mitigations"]` so `_apply_background_dynamics` (which
keys its task-specific state transitions off that set, not raw `actions_taken`) and
`_can_resolve()` both respect the same gate. Task definitions (starting state, hints
revealed by each inspect action, required mitigations, optimal action sequence) live in
`tasks/task_config.py` — `_apply_action` and `_apply_background_dynamics` both branch on
`self.task`, so adding a scenario means updating task_config *and* both of those methods in
`env/environment.py`. `optimal_actions` is generated by `scripts/derive_optimal.py` from the
Q* solver, not hand-written — rerun it after any change to env dynamics, `MITIGATION_PREREQS`,
or task config.

**Server:** `server/app.py` exposes the OpenEnv HTTP interface (`/reset`, `/step`, `/state`,
`/score`, `/episode`, `/demo`, `/leaderboard`, `/tasks`, `/health`) over `DevOpsEnv`.
`server/inference.py` talks to a configured LLM (OpenAI-compatible API, env vars
`API_BASE_URL`/`MODEL_NAME`/`HF_TOKEN`/`OPENAI_API_KEY`/`API_KEY`) for `/demo`; without one it
falls back to a labeled heuristic baseline. `app.py` at the repo root is the FastAPI entry
point (`app_file` per `openenv.yaml`/Dockerfile) and also serves `static/index.html`, a 3-tab
ops console (simulate / results / leaderboard).

**Training package** (`training/`, extracted from a formerly-monolithic `train.py`):
- `config.py` — `TrainConfig` dataclass loaded from `config/train.yaml` (single source of
  truth for hyperparameters), overridable via env vars (`GRPO_MAX_STEPS`, `HF_TOKEN`, etc.)
- `qstar.py` — exact Q* solver: depth-indexed BFS + backward value induction over the env's
  finite, deterministic state space (falls back to a width-60 beam search on tasks where exact
  search doesn't terminate — verified equal wherever both ran), cached to
  `outputs/qstar_<task>.json` keyed by a hash of task config + `MITIGATION_PREREQS` + branch
  action set, so it invalidates automatically when Phase-A-style env changes land
- `dataset.py` — `generate_sft_dataset()` walks each held-in task's optimal trajectory;
  `generate_grpo_dataset()` draws from `iter_eps_greedy_states()`, an eps-greedy walk (probability
  `epsilon` of a random action from `qstar.relevant_actions(task)` instead of the Q*-optimal one)
  that expands the GRPO prompt set well beyond what SFT already memorised, with zero state
  overlap between the two by construction and `memory_leak`/`disk_full` excluded from both
- `reward_functions.py` — `ALL_REWARD_FUNCTIONS` = format + `qstar_reward_func` (primary signal:
  `Q*(s,a) - max_a' Q*(s,a')`) + diversity; the original 9 hand-tuned functions are retired to
  `LEGACY_REWARD_FUNCTIONS` (kept importable/tested for ablation, not wired into training).
  `diversity_reward` is deliberately scored *per completion* rather than per group, since a
  reward uniform across a GRPO group is cancelled by the group-mean baseline and produces no
  gradient
- `prompting.py` — `SYSTEM_PROMPT` + `build_prompt`, shared by training, `scripts/evaluate.py`,
  and `compare_inference.py` so prompt format never drifts between train and eval
- `pipeline.py` — the SFT→GRPO loop; asserts at startup that the longest training prompt fits
  `max_prompt_length` and raises rather than let TRL silently left-truncate (which would strip
  the system prompt)
- `callbacks.py`, `plot.py` — reward logging/plotting (incl. a `reward_std` collapse panel)

**Grading:** `graders/grader.py::compute_score()` is a deterministic, 5-component weighted
score (diagnosis quality, mitigation completion, recovery, communication richness, efficiency)
over `[0, 1]`, used both as the terminal env score and as the delta source for step rewards.

## Known constraints worth knowing before touching training config

- `lora_alpha` must stay `2 * lora_rank` (currently 64/32) — at a 1:1 ratio the LoRA update
  is scaled by 0.5.
- `max_prompt_length` (1024) must exceed the ~700-token median prompt with margin; TRL
  left-truncates silently past this, which removes the system prompt.
- `kl_coef` (0.005, TRL's `beta`) — 0.04 was found to over-anchor the policy to the SFT
  reference and suppress learning.
- `max_seq_length` must fit `max_prompt_length + max_completion_length`.
- `train_tasks`/`eval_tasks` in `config/train.yaml` must stay disjoint — SFT and GRPO both
  filter on `train_tasks`, and evaluating held-out generalisation on a task that leaked into
  training silently invalidates the eval.

## Tests

102 tests total, CPU-only, no model loading (`tests/conftest.py` + 7 files covering reward
functions, environment/tasks (incl. mitigation-gating), grader, a reward-ranking tripwire,
dataset generation, config/hardware-profile resolution, and the backend seam).
`test_backend.py` includes a source-level tripwire that `training/pipeline.py` calls
`backend.preimport(config)` before `from trl import ...` — Unsloth patches trl at import
time and, imported second, rewrites `SFTConfig`'s `eos_token` default to the placeholder
`"<EOS_TOKEN>"`, which `SFTTrainer` rejects as out-of-vocabulary
(unslothai/unsloth#2797). That failure only surfaces minutes into a GPU run.
`test_reward_ranking.py` hard-asserts the reward stack ranks a Q*-optimal
action first in every training state — this is a structural property of `qstar_reward_func`
(reward *is* the grader, maximised), not something tuned toward, so a regression here means the
bug is in `training/qstar.py` or in how a reward stack composes it, not in the test.

When making multiple related code changes, do not run tests after each individual edit. Batch all planned changes first, then run the full test suite once at the end. Only run a targeted test immediately if a change is high-risk or isolated.
